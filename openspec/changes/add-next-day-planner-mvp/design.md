## Context

当前后端已经有 `DailyPlan`、`TimeBlock`、`PlannerService` 和 `ai.Planner`，前端也有基础的计划页，但实现仍然是“读取任务后直接生成 today plan”。它依赖 `User` 上少量时间偏好字段与 mock planner 的线性排程，无法表达以下 V1 核心需求：

- 固定作息和固定不可安排时间
- 重复习惯占位
- 手动输入当天/近期上下文
- 先遵守硬约束，再生成柔性任务块
- 为每个计划块展示说明、目标和产出

项目当前按单用户模式推进，但代码中仍保留 `user_id` 作为数据归属键，因此本次设计保持单用户产品假设，同时继续沿用现有仓储和接口风格。

## Goals / Non-Goals

**Goals:**

- 为固定作息和重复习惯建立独立的数据模型与持久化能力。
- 将次日规划流程重构为“规则排班 + LLM 丰富”的两阶段生成。
- 扩展日计划结果模型，使页面能展示每段计划的说明、目标和预期产出。
- 提供一个完整的前端闭环：配置约束、输入上下文、生成次日规划、查看结果。
- 为输入校验、约束冲突和生成失败提供基础错误处理。

**Non-Goals:**

- 不实现多日连续优化排程。
- 不接入外部 Todo 或日历系统。
- 不引入多用户权限、登录或协作。
- 不在 V1 中做完整任务管理改造；现有任务/目标能力只作为补充输入来源。

## Decisions

### 1. 将作息和习惯抽象为统一的硬约束来源，但保留独立实体

新增两类配置实体：

- `ScheduleRule`: 表达固定作息或固定不可安排时间段，核心字段包括名称、开始/结束时间、适用日期类型、是否锁定。
- `HabitRule`: 表达重复习惯，核心字段包括名称、持续时长、时间偏好、适用星期、是否必须执行。

在生成次日规划时，这两类数据都会被转换为统一的 `HardConstraintBlock` 内存结构，再交给规则层占位。

这样设计的原因：

- 产品层面上“作息”和“习惯”是两个不同配置入口，保留独立实体更符合用户心智和页面组织。
- 规则层面上二者都属于不可随意覆盖的硬约束，统一转换后更方便排班。

备选方案是直接设计一个通用 `HardConstraint` 表，通过 `type` 区分来源。该方案表更少，但会把表单校验、字段语义和前端交互耦合在一起，不利于 V1 快速做出清晰页面。

### 2. 为次日规划新增独立输入对象，而不是继续复用 `hint` 文本

当前 `GeneratePlan` 只有 `date` 和 `hint`。本次会引入结构化请求，例如：

- `target_date`
- `context_text`
- `anchored_items`：已有明确时间的临时事项，如会议
- `focus_items`：希望明天推进的事项

后端会先对请求做校验，并把 `anchored_items` 一并视为硬约束来源。

这样设计的原因：

- 单一 `hint` 过于松散，无法支撑规则排班和可测试校验。
- 结构化字段允许后续平滑接入任务、项目和学习进度，而不需要重写接口。

备选方案是继续只传自然语言，再由 LLM 提取。该方案实现更快，但不满足“规划不会占用硬约束时间”的稳定性要求。

### 3. 生成链路拆成“规则层产出时间窗”与“LLM 层补全内容”

规划服务会重构为以下步骤：

1. 读取目标日期的 `ScheduleRule`、`HabitRule` 和本次请求中的临时锚点事项。
2. 生成当天硬约束块，并做冲突校验。
3. 在剩余可用时间中生成候选时间窗，按时间偏好、优先级和估时做规则分配。
4. 将已分配的时间窗、上下文和候选事项交给 `ai.Planner`，由其补全块说明、目标、产出和摘要。
5. 持久化 `DailyPlan` 与 `TimeBlock`。

关键点是 LLM 不再负责决定“是否能排进去”，而只负责在合法时间窗上做内容增强。

这样设计的原因：

- 硬约束保护是 V1 的核心可信度来源，必须由确定性逻辑保证。
- LLM 仍保留对上下文理解、输出补全和自然语言说明的优势。

备选方案是完全规则生成所有文案。该方案更稳，但会让“目标/产出/提醒”的质量太差，难以体现产品价值。

### 4. 扩展计划块结构，直接承载页面展示所需字段

现有 `TimeBlock` 只有 `title` 和 `note`，不足以表达页面要求。本次扩展为至少包含：

- `title`
- `description`
- `goal`
- `expected_output`
- `source_type`，标记来自作息、习惯、上下文事项或任务
- `is_locked`

前端页面直接消费这些字段，不再在渲染层拼接说明文案。

这样设计的原因：

- “说明、目标、产出”是用户可见结果，不应塞进单一 `note` 字段。
- 把语义提前固化到模型，可降低前端展示逻辑复杂度。

备选方案是把这些内容序列化到 `note` 中。该方案迁移最少，但结构不稳定，也不利于后续测试。

### 5. 保持单用户产品模式，但不移除现有 `user_id`

所有新增配置和规划结果继续按 `user_id` 组织，页面默认操作当前固定用户。这样可以复用现有 repository / handler 结构，也避免未来恢复多用户时再做二次迁移。

## Risks / Trade-offs

- [规则模型过重] → V1 只支持按星期重复、固定开始结束时间和固定持续时长，不引入复杂 recurrence 规则。
- [LLM 输出与规则结果不一致] → LLM 只接收已锁定时间窗，返回结果时由服务层再次校验时间边界，不允许覆盖起止时间。
- [现有 today plan 语义与次日规划冲突] → 统一改为显式传入 `target_date`，前端默认生成“明天”而不是“今天”。
- [数据模型改动较多] → 通过新增表和向后兼容字段扩展完成，避免破坏已有 `goal/task` 数据。
- [前端页面跨度较大] → V1 先在单页内完成“配置 + 生成 + 查看”闭环，不拆分复杂多路由设置中心。

## Migration Plan

1. 新增数据库表或模型：`schedule_rules`、`habit_rules`，并扩展 `daily_plans` / `time_blocks` 字段。
2. 为 repository、service、handler、frontend API 增加对应读写能力。
3. 用规则排班器替换当前 mock planner 的时间分配职责；mock/LLM 仅负责内容增强。
4. 更新前端计划页，默认目标日期为次日，加入配置和上下文输入。
5. 验证旧数据仍可读取；如旧 `TimeBlock.note` 存在，页面继续兼容展示。
6. 若发布后生成链路异常，可回退为只读旧计划展示，同时关闭新的生成入口。

## Open Questions

- V1 是否需要允许用户手动编辑生成后的时间块，还是先只支持重新生成。
- “重复习惯”是否必须支持多个时间偏好档位，例如晚间优先、任意可用时间。
- 上下文中的“未定项提醒”是否落为独立计划块，还是只进入摘要与说明文本。
